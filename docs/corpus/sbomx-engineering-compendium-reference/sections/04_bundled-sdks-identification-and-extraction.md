## 4. Bundled SDKs: Identification and Extraction

### SDK Manifest Parsing and Metadata Extraction

The parsing and extraction of metadata from SDK manifests are pivotal steps in identifying and analyzing bundled SDKs within mobile applications. These processes rely on structured formats such as JSON and XML, which are commonly used in SDK manifest files to describe components, dependencies, and versioning information. The first stage involves reading the manifest file, which typically resides in a predefined location within the app's directory structure. For example, in Android apps, the `AndroidManifest.xml` file is a primary source of metadata, while iOS apps may use `Info.plist` or third-party SDK-specific manifests. These files are parsed using standard XML or JSON parsers, such as Java’s `javax.xml.parsers` or Python’s `xml.etree.ElementTree`, which extract key-value pairs that describe the SDK’s properties.

Once parsed, metadata extraction focuses on identifying critical attributes such as the SDK name, version, vendor, and dependencies. These attributes are often embedded within specific elements of the manifest file. For instance, in an Android SDK manifest, the `<manifest>` tag may contain attributes like `package`, `versionName`, and `versionCode`, which provide essential information about the SDK’s identity and versioning. Similarly, in iOS SDK manifests, the `<dict>` element may include keys such as `CFBundleIdentifier`, `CFBundleVersion`, and `CFBundleShortVersionString`. These metadata fields are then mapped to standardized identifiers, such as the Common Vulnerabilities and Exposures (CVE) identifier or the CycloneDX SBOM component schema, enabling the integration of SDK information into a comprehensive software bill of materials (SBOM).

The versioning information extracted from SDK manifests is particularly crucial for vulnerability detection. Version numbers are typically stored in semantic format, such as `1.2.3`, which allows for precise comparisons against known-vulnerability databases like the National Vulnerability Database (NVD). For example, if an SDK manifest specifies a version `1.2.5` and the NVD lists a vulnerability affecting versions up to `1.2.4`, the parser can flag this discrepancy as a potential security risk. This process is further enhanced by using version comparison libraries like `semver` in Node.js or `packaging.version` in Python, which provide robust mechanisms for parsing and comparing semantic version strings.

In addition to versioning, metadata extraction also involves identifying dependencies declared within the SDK manifest. These dependencies are often listed as nested elements or sub-elements within the main manifest structure. For instance, in an Android SDK manifest, dependencies may be specified under the `<uses-library>` or `<library>` tags, while in iOS SDK manifests, they might appear as `CFBundleDependencies` or `CFBundleURLTypes`. These dependencies are then parsed into a list of component identifiers, which can be cross-referenced against known component databases like the Open Source Vulnerability Database (OSV) or the CycloneDX SBOM registry. This step is essential for mapping each dependency to its corresponding component in the SBOM, ensuring that all bundled SDKs and their dependencies are accurately represented.

The parsing of SDK manifest files also includes the extraction of vendor information, which is critical for attributing vulnerabilities and tracking the origin of components. Vendor details are often stored in attributes such as `vendor` or `publisher`, which can be explicitly specified in the manifest or inferred from the component name. For example, an SDK named `com.example.sdk` may have its vendor identified as `example.com` through a lookup in a vendor registry or by analyzing the component’s namespace. This information is then used to map the SDK to its corresponding entry in the SBOM, ensuring that all relevant metadata is included in the final bill of materials.

Another critical aspect of metadata extraction is the identification of component identifiers, which are essential for linking SDKs to their respective entries in vulnerability databases. Component identifiers are typically derived from the SDK’s name, version, and vendor information, and are often formatted using standardized schemes such as `org.cyclonedx:component:1.0` or `maven:groupId:artifactId:version`. These identifiers are then mapped to known components in repositories like the Maven Central Repository or the npm Registry, enabling precise vulnerability matching. For example, if an SDK manifest specifies a component identifier `com.example.sdk:1.2.3`, the parser can query the CycloneDX SBOM registry to determine whether this component exists and what vulnerabilities it may be associated with.

The parsing and extraction of metadata from SDK manifests are also influenced by the specific structure and syntax of the manifest file. For example, in some SDKs, the manifest may include additional metadata fields such as `license`, `copyright`, or `privacy-policy`, which provide valuable information for compliance and risk assessment. These fields are parsed using standard text processing techniques, such as regular expressions or tokenization, to extract key-value pairs that can be integrated into the SBOM. For instance, a license field specified as `Apache-2.0` can be mapped to the SPDX license identifier `Apache-2.0`, ensuring that all licensing information is accurately represented in the final bill of materials.

The parsing process also involves handling nested or hierarchical structures within SDK manifest files, which may contain multiple levels of dependencies and metadata. For example, an Android SDK manifest may include `<application>` tags that contain nested `<activity>` or `<service>` elements, each of which may have its own set of attributes and dependencies. These nested structures are parsed recursively, ensuring that all relevant metadata is captured and integrated into the SBOM. This recursive parsing is particularly important for identifying complex dependency chains that span multiple SDKs and libraries.

In addition to structured formats like JSON and XML, some SDKs use alternative manifest formats such as YAML or custom binary formats. These formats require specialized parsers that can handle their unique syntax and structure. For example, a YAML-based manifest file may use indentation and key-value pairs to describe components, while a binary manifest may require deserialization using specific libraries or tools. These parsers are often integrated into the SBOM generation pipeline, ensuring that all SDKs, regardless of their manifest format, are accurately parsed and extracted.

The metadata extraction process is further enhanced by leveraging external databases and registries that provide additional context about SDKs and their components. For example, the CycloneDX SBOM registry contains a comprehensive list of known components, each with associated metadata such as version, vendor, and license information. By cross-referencing extracted metadata against this registry, the parser can validate component identifiers and ensure that all bundled SDKs are accurately represented in the SBOM. This validation step is critical for identifying any discrepancies or missing information in the manifest file.

Finally, the parsed metadata from SDK manifests is structured into a standardized format that aligns with the CycloneDX SBOM schema. This involves mapping extracted attributes to the appropriate fields in the SBOM, such as `name`, `version`, `vendor`, and `dependencies`. The resulting SBOM component entries are then validated against the schema to ensure consistency and completeness. This step is essential for generating a high-quality SBOM that accurately reflects the components and dependencies of the mobile application.

In summary, the parsing and extraction of metadata from SDK manifests are foundational steps in identifying and analyzing bundled SDKs within mobile applications. These processes rely on structured formats such as JSON and XML, which are parsed using standard libraries and tools. The extracted metadata, including versioning information, dependencies, and vendor details, is then mapped to standardized identifiers and integrated into the SBOM. By leveraging external databases and registries, the parser ensures that all SDKs and their components are accurately represented, providing a comprehensive and actionable bill of materials for security and compliance purposes.

### Binary Analysis for Embedded SDKs

Binary analysis is a critical phase in the identification and extraction of embedded SDKs within mobile applications. Unlike traditional library dependencies that are often declared in manifest files or build configurations, embedded SDKs are frequently included as native binaries or compiled libraries, making them invisible to conventional dependency resolution tools. This necessitates the use of advanced binary analysis techniques to uncover these components, which may be obfuscated or packed within the application’s binary footprint. The process begins with static analysis of the application binary, leveraging disassemblers and decompilers to inspect the structure and composition of the code.

At the core of this analysis is the ability to identify segments of the binary that correspond to SDK code. Tools such as IDA Pro, Ghidra, and Radare2 enable developers and analysts to inspect the binary at the machine instruction level, allowing for the detection of API calls, function signatures, and data structures that are indicative of embedded SDKs. For example, in a mobile application built with native code using the Android NDK or iOS Objective-C runtime, embedded SDKs may introduce unique method names, class hierarchies, or memory layouts that distinguish them from the core application logic. By analyzing these patterns, analysts can pinpoint the presence of third-party SDKs within the binary.

One of the most effective techniques for identifying embedded SDKs is signature-based detection. This involves comparing segments of the binary against known signatures of SDKs, which are often derived from their source code or decompiled versions. For instance, Firebase SDKs may include specific function calls such as `FirebaseApp.initializeApp()` or `FirebaseDatabase.getInstance()`, which can be detected through pattern matching in the disassembled code. Similarly, SDKs such as Google Maps or AdMob may introduce unique constants or strings that serve as markers for their presence. These signatures are often compiled into databases or rule sets that can be used by automated tools to scan binaries for known SDKs.

Another approach is to analyze the binary's import and export tables, which list the functions that the binary depends on or provides. In Windows-based applications, this is typically found in the `.idata` section of the PE file format, while in Linux-based applications, it may be located in the `.dynamic` section of the ELF file. By inspecting these sections, analysts can identify external libraries or frameworks that are being used by the binary. For example, an embedded SDK such as Fabric (now part of Firebase) might import functions from its native libraries, which can be detected by examining the import table for references to specific symbols.

In addition to static analysis, dynamic analysis techniques can also be employed to identify embedded SDKs. Tools such as Frida or GDB allow analysts to attach to a running application and monitor its behavior in real-time. This can be particularly useful for detecting SDKs that are loaded dynamically at runtime, such as those that use dlopen or dlsym on Linux or LoadLibrary on Windows. By intercepting function calls and monitoring memory allocations, analysts can observe how the SDK interacts with the application and identify its presence.

One of the challenges in binary analysis is distinguishing between embedded SDKs and core application code. To address this, analysts often employ a combination of static and dynamic techniques, along with heuristic analysis to infer the purpose of certain code segments. For example, if a segment of code contains a large number of function calls that are not present in the core application logic, it may be indicative of an embedded SDK. Similarly, the presence of specific data structures or memory patterns can help differentiate between native code and SDK code.

To further refine the identification process, analysts can use machine learning techniques to classify segments of the binary based on their characteristics. By training a model on a dataset of known SDK binaries, the model can learn to recognize patterns that are common across different SDKs. This approach is particularly useful for identifying less common or newer SDKs that may not have well-documented signatures.

In practice, the identification of embedded SDKs often involves a multi-step process. Analysts begin by performing a static analysis of the binary to identify potential SDK candidates. They then use dynamic analysis tools to observe the behavior of these candidates and confirm their presence. Finally, they cross-reference the findings with known SDK databases to ensure accurate identification.

For example, consider an application that includes the Google Maps SDK as an embedded component. Static analysis might reveal segments of code that reference specific functions related to map rendering or geolocation services. Dynamic analysis could then show these functions being called during runtime, confirming the presence of the SDK. By combining these techniques, analysts can confidently identify and extract the embedded SDK from the application binary.

In summary, binary analysis is a powerful tool for identifying embedded SDKs within mobile applications. By leveraging static and dynamic analysis techniques, along with signature-based detection and heuristic reasoning, analysts can uncover these components even when they are not explicitly declared in the application’s manifest or build configuration. This process is essential for accurately mapping out the component dependencies of a mobile application and ensuring that all embedded SDKs are accounted for in the software bill of materials (SBOM). The next step in this process involves the extraction of these SDKs from the binary, which will be explored in the following section.

### Resource File Inspection for SDK References

Resource file inspection is a critical step in identifying bundled SDKs within mobile applications, particularly when these SDKs are embedded as native libraries or compiled into the application binary. Unlike manifest files or metadata that explicitly declare dependencies, resource files often contain indirect references to SDK components that are not immediately visible through traditional analysis techniques. These files may include configuration data, binary assets, or serialized objects that retain traces of the SDKs used during development. Therefore, inspecting resource files becomes an essential method for uncovering embedded SDKs, especially when they are obfuscated or dynamically loaded at runtime.

The primary resource file formats in mobile applications are Android's `AndroidManifest.xml`, `res/` directories containing XML and binary assets, and iOS's `Info.plist`. While the `AndroidManifest.xml` is typically used to declare application-level dependencies, it often does not list all bundled SDKs, especially those that are compiled into native libraries or embedded as resources. Instead, the `res/` directory contains a wealth of information about the app’s assets, including images, layouts, and serialized data structures such as JSON or XML files that may encode SDK-specific metadata.

One concrete example is the use of `AndroidManifest.xml` to identify SDKs through declared permissions or package names. However, this approach can be limited when SDKs are not explicitly declared in the manifest. In such cases, resource files like `res/values/strings.xml`, `res/xml/` directories, or even `res/raw/` files may contain embedded references to SDKs. For instance, a mobile advertising SDK might inject its own configuration file into the app’s resources, which includes identifiers such as `com.admob.sdk` or `com.google.ads`. These identifiers can be extracted and matched against known SDK repositories or databases of bundled components.

Another important resource file is the `AndroidManifest.xml` itself, which may include `<uses-library>` tags that reference native libraries. These tags are often used for Android Native Development Kit (NDK) libraries, such as those written in C++ using the `jni/` directory structure. By parsing these tags, developers and analysts can identify the presence of native SDKs that are not declared elsewhere in the manifest. For example, a mobile payment SDK might be bundled as a native library under the `jni/lib` directory, and its presence can be confirmed by checking for corresponding entries in the manifest.

In addition to manifest files, resource files such as `res/xml/` directories may contain XML-based configuration data that includes SDK-specific information. For instance, an analytics SDK might inject its own tracking configuration into a file like `res/xml/tracking_config.xml`, which could include details such as API keys, endpoint URLs, or SDK version numbers. These files can be parsed using standard XML parsing tools and then cross-referenced with known SDK signatures or versioning schemes.

Similarly, in iOS applications, the `Info.plist` file may contain references to bundled frameworks or libraries, but these references are often indirect. For example, a framework might be embedded as a `.framework` directory within the app bundle, and its presence can be detected by inspecting the contents of the `Frameworks/` directory. However, this approach may not always capture all SDKs, especially those that are dynamically linked or loaded at runtime. In such cases, resource files like `Resources/` directories or compiled assets may contain traces of SDK usage, which can be analyzed using reverse engineering tools.

A more advanced technique involves inspecting binary resources such as images, icons, or serialized objects for embedded SDK identifiers. For example, a mobile app might include an image that contains a watermark or logo from an advertising SDK. These images can be extracted and analyzed using image processing tools to detect patterns or text that indicate the presence of a specific SDK. Similarly, serialized data structures such as JSON or XML files might contain metadata that reveals the use of a particular SDK, even if it is not explicitly declared in the manifest.

Another approach is to analyze the app’s compiled resources for embedded SDK-specific signatures. For example, an SDK might inject its own version number or unique identifier into a resource file, which can be extracted and matched against known SDK signatures. This technique is particularly useful when dealing with SDKs that are not explicitly declared in the manifest but are nonetheless embedded within the application.

In addition to these methods, resource files may also contain traces of SDK usage through dynamic loading mechanisms such as `dlopen` or `LoadLibrary`. These functions allow SDKs to be loaded at runtime, making it more difficult to identify them through static analysis. However, by inspecting the app’s binary for calls to these functions, analysts can detect the presence of dynamically loaded SDKs and then trace their usage through resource files or other embedded data.

Overall, resource file inspection provides a powerful method for identifying bundled SDKs in mobile applications. By analyzing manifest files, configuration data, binary assets, and serialized objects, analysts can uncover indirect references to SDKs that may not be explicitly declared elsewhere. This approach is particularly useful when dealing with obfuscated or dynamically loaded SDKs, as it allows for a more comprehensive understanding of the application’s component dependencies. Through careful parsing and cross-referencing with known SDK repositories, resource file inspection becomes an essential tool in the broader process of identifying and extracting bundled SDKs from mobile applications.

### Dynamic Loading Detection in Native Libraries

Dynamic loading detection in native libraries is a critical step in unpacking bundled SDKs, as it enables the identification of components that are loaded at runtime rather than being statically linked. This process is essential for accurately mapping the dependencies and potential vulnerabilities associated with each component within the mobile application. Dynamic loading refers to the practice of loading shared libraries (such as `.so` files on Android or `.dylib` files on iOS) during execution, rather than at compile time. This technique allows for greater flexibility and modularity but also introduces complexity in tracking and analyzing the components involved.

The detection of dynamically loaded native libraries typically involves inspecting the binary structure of the application and identifying references to external shared libraries. On Android, this can be achieved by examining the `AndroidManifest.xml` file or using tools like `readelf` or `nm` to analyze the symbol table of the compiled application. These tools can reveal which libraries are explicitly referenced and whether they are loaded dynamically at runtime. For example, a library such as `libsqlite3.so` may be dynamically loaded by an application through calls to `dlopen()` or `System.loadLibrary()`. Similarly, on iOS, dynamic loading is often facilitated by the `dyld` loader, which can be inspected using tools like `otool` or `nm` to identify dynamically linked libraries.

One of the most common mechanisms for detecting dynamically loaded native libraries is through the use of the `dlopen()` function in C and C++ applications. This function allows an application to load a shared library at runtime, which can be useful for loading plugins or modules on demand. However, this also means that the presence of such calls in the application's code can indicate the use of dynamically loaded libraries. For example, an Android application may include a call to `System.loadLibrary("mylibrary")`, which instructs the system to load the corresponding shared library at runtime. This call is typically found in the native code section of the application and can be detected by analyzing the source code or using static analysis tools.

In addition to explicit calls to functions like `dlopen()` or `System.loadLibrary()`, dynamic loading can also be inferred from the presence of unresolved symbols in the application's binary. These unresolved symbols indicate that the application is expecting certain functions or variables to be provided by external libraries at runtime. For example, if an application references a function such as `sqlite3_open` but does not define it within its own code, it is likely that the application is dynamically linking to the SQLite library. This can be detected using tools like `nm`, which lists the symbols present in a binary, or by analyzing the output of `readelf` on Linux-based systems.

Another important aspect of dynamic loading detection is the identification of inter-library dependencies. When an application dynamically loads a shared library, it may also depend on other libraries that are required for that library to function correctly. These dependencies can be identified using tools like `ldd` on Linux or `otool -L` on macOS. For instance, if an application dynamically loads `libsqlite3.so`, it may also depend on `libz.so` for compression functionality. By analyzing these dependencies, we can build a more complete picture of the application's component structure and identify potential vulnerabilities associated with each library.

The detection of dynamically loaded native libraries is not limited to code-level analysis. It can also be inferred from runtime behavior using dynamic analysis tools such as `gdb`, `strace`, or `lldb`. These tools allow us to monitor the application's execution and observe when shared libraries are loaded at runtime. For example, by using `strace` on an Android application, we can see when `dlopen()` is called and which library is being loaded. This information can then be used to build a more accurate representation of the application's component graph.

In iOS applications, dynamic loading is often facilitated by frameworks such as `dyld`, which manages the loading of shared libraries at runtime. The presence of certain symbols or functions in the application's binary can indicate that it is dynamically linked to other libraries. For example, an iOS application may use the `NSBundle` class to load resources from a bundle, which can include dynamically linked libraries. By analyzing the application's binary using tools like `otool`, we can identify these dynamic dependencies and map them to their respective components.

The detection of dynamically loaded native libraries is also important for identifying potential security vulnerabilities. Many known vulnerabilities are associated with outdated or insecure versions of shared libraries, and the ability to accurately track which libraries are being used can help in identifying and mitigating these risks. For example, if an application dynamically loads a version of `libssl.so` that is known to have a critical vulnerability, it may be necessary to update the library or patch the application to address the issue.

In summary, dynamic loading detection in native libraries is a crucial step in unpacking bundled SDKs and accurately identifying the components involved. By analyzing the binary structure of the application, detecting explicit calls to dynamic loading functions, and identifying inter-library dependencies, we can build a more complete understanding of the application's component graph. This process not only helps in identifying potential vulnerabilities but also provides valuable insights into the application's architecture and dependencies. The use of tools such as `readelf`, `nm`, `ldd`, and `otool` enables the accurate detection of dynamically loaded libraries, which is essential for generating a comprehensive SBOM and ensuring the security and integrity of mobile applications.

The process of detecting dynamically loaded native libraries also involves examining the application's runtime behavior to identify when shared libraries are loaded. This can be done using dynamic analysis tools such as `strace` on Linux-based systems or `lldb` on macOS. These tools allow us to monitor the execution of the application and observe when specific functions, such as `dlopen()` or `System.loadLibrary()`, are called. For example, by running an Android application under `strace`, we can see exactly which shared libraries are being loaded at runtime. This information is critical for identifying all the components that are dynamically linked to the application, including any third-party SDKs or native modules that may have been bundled with the application.

In addition to detecting dynamic loading through explicit function calls, it is also possible to infer the presence of dynamically loaded libraries by analyzing the application's binary for unresolved symbols. In summary, the detection of dynamically loaded native libraries is a multifaceted process that involves both static and dynamic analysis techniques. ### Dependency Graph Construction from SDK Artifacts

The construction of a dependency graph from SDK artifacts is a critical step in the process of generating a CycloneDX SBOM for mobile applications. This task involves analyzing the bundled SDKs and their associated native libraries to identify all components, dependencies, and relationships that exist within the application’s artifact set. The goal is to create a structured representation of how these components interconnect, enabling accurate vulnerability mapping and risk assessment. To achieve this, the process begins with the identification of SDK artifacts, followed by the extraction of their internal structure. Once extracted, each component is analyzed for its dependencies, which are then mapped into a graph that reflects both direct and transitive relationships.

The first step in constructing the dependency graph is to unpack the SDK artifacts and identify all constituent files. This typically involves using tools such as `apktool` for Android applications or `otool` for macOS frameworks, which allow developers to decompile and inspect the contents of an application package. These tools provide visibility into the internal structure of the SDK, revealing not only the primary libraries but also any embedded resources or additional dependencies. For example, in an Android application, the `AndroidManifest.xml` file can be used to identify the SDKs that are explicitly declared as dependencies. However, many SDKs may also include native libraries (e.g., `.so` files for Android or `.dylib` files for macOS) that are not explicitly listed in the manifest, necessitating a more thorough inspection of the artifact’s contents.

Once the artifacts are unpacked, the next phase involves identifying and cataloging each component. This is typically done by scanning the extracted files for known file types, such as Java bytecode, C++ object files, or dynamic libraries. Each identified component is then assigned metadata, including its name, version, and checksum, which can be used to match it against known vulnerability databases. For instance, a native library named `libopencv.so` might be matched against the OpenCV project’s repository to determine its version and associated vulnerabilities. This process requires a combination of automated analysis tools and manual inspection, particularly when dealing with complex or proprietary SDKs that may not follow standard naming conventions.

The extraction of dependencies from SDK artifacts is a more nuanced task, as it involves identifying both direct and transitive dependencies. Direct dependencies are those explicitly included in the SDK’s manifest or build configuration, such as libraries listed in the `build.gradle` file for Android or the `Podfile` for iOS projects. Transitive dependencies, on the other hand, are those that are pulled in automatically due to the inclusion of a higher-level library. For example, if an SDK includes a library for image processing, it may also pull in libraries for compression or rendering, which must be identified and included in the dependency graph.

To extract these dependencies, tools such as `gradle dependencies` for Android or `pod lib lint` for iOS can be used to generate a list of all dependencies, including their versions. However, these tools may not always provide complete information, particularly when dealing with native libraries that are not managed through standard package managers. In such cases, static analysis tools like `readelf` for ELF files or `nm` for symbol tables can be employed to inspect the contents of native libraries and identify any external dependencies they may have. These tools can reveal which shared libraries a given binary is linked against, allowing for the construction of a more accurate dependency graph.

In addition to identifying dependencies, it is essential to map out the relationships between components. This involves determining which components are directly dependent on others and how these dependencies propagate through the application’s artifact set. For example, if an SDK includes a library `A` that depends on library `B`, then the dependency graph must reflect this relationship as a direct edge from `A` to `B`. Furthermore, any transitive dependencies that arise from `B` (e.g., `C`) must also be included in the graph, creating a chain of dependencies that spans multiple components.

This mapping is often facilitated by using tools that can parse the metadata of each component and build a graph based on the relationships between them. For instance, the `mvn dependency:tree` command for Maven projects generates a tree-like structure of all dependencies, which can be used to construct a dependency graph. Similarly, tools like `npm ls` or `yarn list` for JavaScript projects provide a visual representation of dependency relationships. However, these tools are typically designed for package managers that handle dependencies in a more standardized manner, and their effectiveness may be limited when dealing with native libraries or SDKs that do not follow such conventions.

To overcome these limitations, the process often involves combining automated analysis with manual inspection. For example, after using `apktool` to unpack an Android application, the resulting directory structure can be analyzed to identify all included libraries. Each library can then be inspected using tools like `readelf` or `nm` to determine its dependencies. These findings are then manually entered into a dependency graph, ensuring that all relationships are accurately captured. This approach is particularly useful when dealing with proprietary SDKs that may not provide detailed metadata or when the dependencies are not explicitly declared in the manifest.

Another critical aspect of constructing the dependency graph is ensuring that each component is uniquely identified and properly categorized. This involves assigning a unique identifier to each component, such as a combination of its name, version, and checksum. These identifiers are then used to match components against known vulnerability databases like the National Vulnerability Database (NVD) or the Common Vulnerabilities and Exposures (CVE) list. By doing so, the dependency graph not only reflects the structure of the application’s dependencies but also provides a basis for identifying potential vulnerabilities.

In summary, the construction of a dependency graph from SDK artifacts is a multi-step process that involves unpacking the SDKs, identifying and cataloging their components, extracting dependencies, and mapping out the relationships between these components. This process requires a combination of automated tools and manual inspection to ensure accuracy, particularly when dealing with complex or proprietary SDKs. The resulting dependency graph serves as a foundational element for generating a comprehensive CycloneDX SBOM, enabling the identification of vulnerabilities and the assessment of risk within the application’s artifact set.

### Version Normalization and Component Mapping

Version Normalization and Component Mapping is a critical phase in the identification and extraction of bundled SDKs, ensuring that the components extracted from mobile applications are accurately represented for subsequent vulnerability analysis and tracking. At its core, this process involves aligning the version identifiers of components with standardized naming conventions and mapping them to known entries in component databases such as the Software Package Data Exchange (SPDX) or the National Vulnerability Database (NVD). This normalization is necessary because native libraries and SDKs often use non-standard or inconsistent versioning schemes, which can obscure their true identity and complicate vulnerability matching.

One of the primary challenges in version normalization is the lack of uniformity in how software components are labeled. For example, a mobile SDK might use a version string like `1.2.3-beta`, while another may employ a semantic versioning format such as `1.2.3+build.456`. These variations can lead to mismatches when comparing component versions against known vulnerabilities or tracking databases. To address this, the CycloneDX SBOM specification recommends using standardized versioning formats, such as Semantic Versioning (SemVer), which follows a strict `MAJOR.MINOR.PATCH` structure and allows for optional pre-release and build metadata. By converting non-standard version strings into SemVer-compatible formats, the SBOM can more accurately represent the component's version and reduce ambiguity.

The normalization process also involves resolving version aliases and synonyms that may exist in component metadata. For instance, a native library might have multiple version identifiers due to different packaging strategies or distribution channels. A common example is when an SDK is distributed as both a `.aar` file and a `.jar` file, each potentially containing slightly different version information. In such cases, the SBOM must reconcile these discrepancies by identifying the canonical version identifier, often based on the primary source of the component or the most recent release. This reconciliation ensures that all references to the same component are consistent, which is essential for accurate vulnerability matching and dependency tracking.

Component mapping extends beyond version normalization by linking the extracted components to their corresponding entries in public databases. This involves querying known component registries such as the NVD, GitHub Packages, or the Open Source Vulnerability Database (OSV) to retrieve metadata about each component, including its name, description, license information, and known vulnerabilities. For example, a bundled SDK identified as `com.example.sdk:1.2.3` might be mapped to an entry in the NVD that contains details about its dependencies and any associated security advisories. This mapping is typically performed using a combination of exact string matching and fuzzy matching algorithms to account for variations in naming conventions or typos.

One concrete mechanism used in component mapping is the use of the Component Identifier (CIdentifier) format, which provides a standardized way to represent components across different ecosystems. The CIdentifier format includes the component's name, version, and optionally, its namespace or repository, allowing for precise identification and differentiation between similar components. For instance, a native library such as `libpng` might be represented as `org.libpng:libpng:1.6.37`, where the first part is the namespace, the second is the component name, and the third is the version. This format is particularly useful when dealing with components that have similar names but different versions or namespaces, ensuring that each entry in the SBOM is uniquely identifiable.

In addition to standardizing component identifiers, mapping also involves resolving dependencies between components. For example, an SDK might depend on multiple libraries, some of which may be native or third-party. By mapping these dependencies to their respective entries in component databases, the SBOM can provide a comprehensive view of the application's component graph, making it easier to identify indirect vulnerabilities that may arise from transitive dependencies. This is particularly important in mobile applications, where the use of bundled SDKs often introduces a complex web of interdependent components.

Another critical aspect of component mapping is the integration of privacy and tracking information. Many bundled SDKs include features such as user data collection or analytics tracking, which can raise privacy concerns. By mapping these components to known privacy databases such as the Privacy Badger database or the Open Privacy Project, the SBOM can provide insights into the potential privacy implications of each component. For example, a mobile SDK identified as `com.example.analytics:2.1.0` might be mapped to an entry in the Privacy Badger database that indicates it collects user location data or sends analytics to a third-party server. This information is crucial for developers and security analysts who need to assess the privacy impact of their application's component ecosystem.

The mapping process also benefits from the use of automated tools and scripts that can query component databases on behalf of the SBOM generator. These tools often leverage APIs such as the NVD API, GitHub API, or the OSV API to retrieve detailed information about each component. For instance, when a component is identified in the SBOM as `org.apache.httpcomponents:httpclient:4.5.13`, an automated script can query the NVD API to fetch any known vulnerabilities associated with that version of the library. This process not only enhances the accuracy of the SBOM but also ensures that the information is up-to-date and relevant.

In some cases, component mapping may require manual intervention, especially when dealing with components that are not well-documented or have ambiguous identifiers. For example, a native library might be identified as `libsqlite3.so` without any version information, making it difficult to map to a specific entry in the NVD. In such cases, developers or analysts must manually cross-reference the component with known versions or use additional metadata such as checksums or build timestamps to determine its exact identity. This manual process is often necessary for components that are not widely used or have limited documentation, but it adds an important layer of precision to the SBOM.

The integration of version normalization and component mapping into the SBOM generation process is essential for ensuring that the resulting SBOM is both accurate and actionable. By standardizing component identifiers and mapping them to known entries in databases, the SBOM provides a clear and consistent view of the application's component ecosystem. This, in turn, enables more effective vulnerability analysis, dependency tracking, and privacy assessment, making it an indispensable part of the software supply chain security workflow.
