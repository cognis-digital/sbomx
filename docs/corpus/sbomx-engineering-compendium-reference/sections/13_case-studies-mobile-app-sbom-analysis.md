## 13. Case Studies: Mobile App SBOM Analysis

### Case Study: Android Banking App with Native Libraries and Third-Party SDKs

The Android banking app under analysis is a complex mobile application that incorporates native libraries and multiple third-party SDKs to deliver advanced financial services. This app is designed for secure transactions, user authentication, and real-time data processing, making it a critical component of the bank's digital infrastructure. The app is built using Java and Kotlin, with a significant portion of its codebase written in C++ for performance-critical operations such as cryptographic computations and low-level device interactions. It includes native libraries such as OpenSSL for secure communication and libpng for image processing, both of which are essential to the app's functionality. Additionally, the app integrates several third-party SDKs, including Google Play Services for location-based features, Firebase for real-time data synchronization, and a proprietary payment gateway SDK for transaction handling.

The use of native libraries in this app is primarily driven by performance requirements and the need for low-level access to hardware features such as secure enclaves and cryptographic accelerators. For instance, the app leverages OpenSSL's AES-NI implementation to accelerate encryption operations, reducing latency during data transmission. Similarly, the integration of libpng ensures efficient image rendering, which is crucial for the app's UI/UX design. These native components are compiled into shared object (`.so`) files and bundled with the app, making them part of the overall software bill of materials (SBOM). However, their inclusion introduces additional complexity in terms of dependency management and vulnerability tracking.

The third-party SDKs in the app further complicate the SBOM analysis. Each SDK represents a separate component with its own set of dependencies, licenses, and potential vulnerabilities. For example, the Google Play Services SDK includes a vast array of modules, some of which are outdated or have known security issues. The Firebase SDK, while generally well-maintained, has been found to contain vulnerabilities such as insecure data storage and insufficient input validation in certain versions. Additionally, the proprietary payment gateway SDK is a custom component developed by the bank's internal development team, which requires careful inspection for potential flaws in its implementation.

The SBOM generation process for this app involves unpacking the native libraries and third-party SDKs to extract their individual components. This is achieved using tools such as `apktool` for decompiling the Android APK file and `dex2jar` for converting Dalvik bytecode into Java bytecode, allowing for a more granular analysis of the app's codebase. Native libraries are extracted using `unzip` or similar utilities, and their contents are analyzed to identify any embedded dependencies or hidden components. Third-party SDKs are similarly unpacked, with their manifest files and resource directories examined to map out their internal structure and dependencies.

Once the components are extracted, the SBOM is generated by cataloging each library and SDK, along with its version, license, and source repository. This process is supported by tools such as CycloneDX, which provides a standardized format for representing software components and their relationships. The resulting SBOM includes detailed information about each component, including its name, version, description, and any associated vulnerabilities. For instance, the OpenSSL library used in the app is identified as `OpenSSL/1.1.1g`, with its license specified as `OpenSSL License`. Similarly, the Firebase SDK is cataloged as `com.google.firebase:firebase-core:20.0.0`, with its license noted as `Apache License 2.0`.

The next step in the SBOM analysis involves matching each component against known-vulnerability databases such as CVE and NVD. This process is automated using tools like `cve-check` and `trivy`, which scan the components for any reported vulnerabilities. For example, the version of OpenSSL used in the app is found to be vulnerable to a specific CVE (CVE-2021-3711), which allows for memory corruption in certain scenarios. Similarly, the Firebase SDK is identified as having a vulnerability related to insecure data storage, which could expose sensitive user information if not properly mitigated.

In addition to known-vulnerability databases, the SBOM analysis also includes matching components against tracker and privacy databases such as GitHub and the Open Source Vulnerability Database (OSV). This helps identify any open-source components that may have been deprecated or have had their licenses changed. For instance, a third-party SDK used in the app is found to have its license updated from `GPLv2` to `MIT`, which could have implications for the app's compliance with certain regulatory frameworks.

The analysis of the native libraries and third-party SDKs reveals several key findings. First, the use of multiple third-party SDKs increases the attack surface of the app, as each SDK may introduce its own set of vulnerabilities. Second, the integration of native libraries such as OpenSSL and libpng requires careful version management to ensure that they are up-to-date and free from known vulnerabilities. Third, the proprietary payment gateway SDK is found to have a potential flaw in its cryptographic implementation, which could be exploited if not properly addressed.

The SBOM analysis also highlights the importance of maintaining an up-to-date dependency tree for the app. By cataloging each component and tracking its version history, developers can more easily identify when updates are needed to address newly discovered vulnerabilities. This is particularly important for the native libraries and third-party SDKs, which often have longer update cycles and may not receive immediate patches for security issues.

In conclusion, the case study of the Android banking app demonstrates the complexity involved in generating an accurate SBOM for a mobile application that incorporates native libraries and third-party SDKs. The process involves unpacking these components, cataloging their details, and matching them against known-vulnerability and privacy databases. The findings from this analysis provide valuable insights into the security posture of the app and highlight the need for ongoing dependency management and vulnerability tracking. By systematically analyzing each component, developers can ensure that the app remains secure and compliant with industry standards.

### Case Study: iOS Fitness Tracker with Embedded Frameworks and Dependency Chains

The iOS fitness tracker case study demonstrates how embedded frameworks and complex dependency chains can significantly complicate SBOM generation and vulnerability analysis. The app, a proprietary fitness application developed by a mid-sized health technology company, includes native code compiled for Apple's ARM architecture and a suite of third-party frameworks bundled into the app bundle. These frameworks are not only essential for core functionality—such as data collection, user interface rendering, and backend communication—but also introduce a layered dependency structure that challenges traditional SBOM methodologies.

The app’s architecture is built around a modular design, where each feature module is encapsulated within its own framework. For example, the "DataAnalytics" framework handles sensor input processing, while the "UserInterface" framework manages screen rendering and gesture recognition. These frameworks are compiled as static libraries, which are then linked into the main application binary during the build process. This approach allows for efficient code reuse but also creates a dependency graph that spans multiple layers of code. The challenge arises when these frameworks themselves depend on other third-party libraries, such as OpenSSL for secure communication, or Firebase for cloud storage and analytics.

The SBOM generation process begins with unpacking the app bundle, which is typically a ZIP file containing the main executable, resources, and embedded frameworks. Using tools like `otool` and `nm`, developers can inspect the binary to identify linked libraries and their versions. However, static linking introduces complications, as it embeds library code directly into the app binary, making it difficult to distinguish between native code and third-party components. To address this, the SBOM must include not only the main application’s dependencies but also those of each embedded framework. This requires recursive unpacking and analysis, often using tools like `swift-package` or `swiftlint` to extract and catalog dependencies.

One of the most significant challenges in this case study is managing the dependency chains that extend beyond the immediate app bundle. For instance, the "DataAnalytics" framework depends on a version of OpenSSL that is not explicitly listed in the main app’s manifest. This version may have known vulnerabilities, such as CVE-2021-3745, which affects older versions of OpenSSL and could expose the app to man-in-the-middle attacks. Similarly, the Firebase SDK used for backend communication includes several subdependencies, including BoringSSL and Protobuf, each of which has its own set of known vulnerabilities. These dependencies are not always visible in the main SBOM, requiring a deeper analysis of the framework’s internal structure.

To accurately capture these dependencies, the SBOM must be generated using a combination of static analysis tools and dynamic dependency resolution. For example, `ldid` can be used to extract the linked libraries from the main executable, while `otool` provides detailed information about the binary’s architecture and linked components. Additionally, tools like `swift-package` or `swiftlint` can be employed to extract dependencies from Swift-based frameworks, ensuring that all third-party components are properly cataloged. This process is further complicated by the fact that some frameworks may use dynamic linking, which requires additional steps to resolve and catalog dependencies at runtime.

Another critical aspect of this case study is the integration of embedded frameworks with the app’s main binary. Since these frameworks are compiled as static libraries, they are tightly coupled with the main application code, making it difficult to isolate their dependencies. For example, a framework like "UserInterface" may depend on a version of UIKit that is different from the one used in the main app. This discrepancy can lead to compatibility issues or security vulnerabilities if the framework’s dependencies are not properly managed. To address this, the SBOM must include detailed information about each framework’s dependencies, including their versions, licenses, and known vulnerabilities.

The SBOM generation process also involves mapping these dependencies to known vulnerability databases such as CVE, NVD, and GitHub Security Advisories. For example, the version of OpenSSL used in the "DataAnalytics" framework may be flagged as having a critical vulnerability, requiring the app developers to update to a newer version or apply a patch. Similarly, the Firebase SDK’s subdependencies may include components with known security issues, such as insecure default configurations or outdated cryptographic algorithms. By mapping these dependencies to their respective vulnerabilities, the SBOM provides a clear picture of the app’s security posture and highlights areas that require immediate attention.

In addition to vulnerability analysis, the SBOM must also account for privacy-related components, such as tracking libraries and data collection frameworks. For instance, the "UserInterface" framework may include a third-party analytics library that sends user data to a cloud service without proper consent. This could violate privacy regulations like GDPR or CCPA, depending on the app’s target audience. By including this information in the SBOM, developers can ensure compliance with relevant laws and regulations, as well as provide transparency to users about how their data is being used.

The case study also highlights the importance of continuous monitoring and updating of dependencies. Even after generating an initial SBOM, new vulnerabilities may be discovered in the components used by the app. For example, a recently disclosed vulnerability in a version of Protobuf used by the Firebase SDK could affect the app’s security if the dependency is not updated. To mitigate this risk, the SBOM should be regularly updated to reflect the latest versions of all components, ensuring that the app remains secure over time.

In conclusion, the iOS fitness tracker case study illustrates the complexities involved in generating an accurate SBOM for mobile apps with embedded frameworks and dependency chains. By unpacking the app bundle, analyzing its internal structure, and mapping dependencies to known vulnerabilities, developers can gain a comprehensive understanding of the app’s security posture. This process not only helps identify potential risks but also ensures compliance with privacy regulations and standards. The case study underscores the importance of rigorous SBOM generation in modern mobile application development, emphasizing the need for continuous monitoring and updates to maintain security and transparency.

Overall, the process of generating an SBOM for this cross-platform e-commerce app involved unpacking native libraries and bundled SDKs, identifying their components, and mapping them to known-vulnerability databases and tracking systems. This comprehensive approach allowed for a detailed analysis of the application's component dependencies and provided valuable insights into its security and privacy implications.

### Case Study: Legacy Mobile Application with Unmaintained Native Libraries

The mobile application under scrutiny, “LegacyApp,” was initially developed in 2016 for Android and iOS platforms using a hybrid framework that integrated native libraries for performance optimization. The app’s primary use case involved real-time data processing and offline storage, which necessitated the inclusion of native components for efficient memory management and low-level system interactions. However, over time, the application’s architecture became increasingly complex due to the addition of multiple third-party SDKs and a growing number of native libraries, some of which were no longer actively maintained. This complexity created a significant risk in terms of security and privacy, as many of these components had known vulnerabilities and outdated dependencies.

The first step in the SBOM analysis involved unpacking the native libraries and bundled SDKs to identify their exact versions and dependencies. The application used a combination of pre-compiled native binaries (in the form of .so files for Android and .dylib for iOS) and dynamically linked libraries, which were often bundled with the app as part of its installation package. These libraries were typically included in the app’s APK or IPA file without clear versioning or metadata, making it challenging to trace their origins and update histories. For example, one of the native libraries, libcrypto.so, was found to be based on an older version of OpenSSL (1.0.2g), which had known vulnerabilities such as CVE-2016-0800 (Heartbleed) and CVE-2015-3864 (POODLE). These vulnerabilities were not patched in the version used by LegacyApp, leaving the app exposed to potential memory leaks and man-in-the-middle attacks.

The SBOM generation process required the use of tools like `apktool` for Android and `class-dump` for iOS to extract the native libraries and SDKs from the application’s package. Once extracted, these components were analyzed using dependency resolution tools such as `Dependency-Check` and `OWASP Dependency-Track` to map out their relationships and identify any known vulnerabilities. The analysis revealed that several of the native libraries were not only outdated but also lacked proper versioning information, making it difficult to determine whether they had been updated in subsequent releases of the app. For instance, one of the SDKs, a custom analytics library named “AnalyticsSDK,” was found to be using an internal versioning system that did not align with standard semantic versioning (SemVer), leading to confusion about its compatibility with other components.

In addition to versioning issues, the native libraries and bundled SDKs were often integrated into the app without proper encapsulation or modularization. This meant that any vulnerability in one component could potentially affect the entire application, increasing the attack surface. For example, a third-party logging library, “LogLib,” was found to be using an unencrypted logging mechanism, which could expose sensitive user data such as session tokens and personal identifiers. This was particularly concerning given the app’s use of offline storage, where user data was stored in encrypted databases but not properly sanitized before being logged. The lack of encryption in the logging library created a potential avenue for attackers to intercept or manipulate logs, leading to data leakage.

The SBOM analysis also uncovered several instances where the native libraries and SDKs were bundled with unnecessary dependencies, increasing the overall size of the application and introducing additional security risks. For example, one of the native libraries, libsqlite3.so, was found to include a dependency on a deprecated version of zlib (1.2.8), which had known vulnerabilities such as CVE-2017-18204 (zlib integer overflow). This dependency was not required for the library’s core functionality, yet it remained included due to the way the library was compiled and bundled. The presence of these unnecessary dependencies not only increased the attack surface but also made it more difficult to update or replace components without affecting other parts of the application.

Another critical issue identified during the SBOM analysis was the lack of transparency in the licensing and privacy practices of some of the bundled SDKs. One of the SDKs, a social media integration library named “SocialSDK,” was found to be using a proprietary license that allowed for data collection without explicit user consent. The SBOM revealed that this SDK included a feature for tracking user behavior across different sessions, which was not clearly disclosed in the app’s privacy policy. This raised concerns about the app’s compliance with data protection regulations such as GDPR and CCPA, particularly given the app’s use of user-generated content and location data.

The SBOM also highlighted the presence of several outdated components that had been included in the application due to a lack of proper dependency management. For example, one of the native libraries, libjpeg.so, was found to be based on an older version of the JPEG library (version 8d), which had known vulnerabilities such as CVE-2017-1675 (JPEG heap overflow). This vulnerability could allow attackers to exploit the library and cause memory corruption, potentially leading to arbitrary code execution. The fact that this library was included in the app without any updates or patches further compounded the risk, as it was not part of the app’s regular update cycle.

The SBOM analysis also revealed that some of the native libraries were compiled with outdated compiler flags and optimization settings, which could introduce additional security risks. For instance, one of the native libraries was compiled using a version of the GNU Compiler Collection (GCC) that did not support modern stack protection mechanisms such as StackGuard or AddressSanitizer. This meant that the library lacked basic protections against stack-based buffer overflows, which could be exploited by attackers to execute arbitrary code. The absence of these protections was particularly concerning given the app’s use of untrusted input sources, such as user-submitted data and third-party API responses.

In addition to the technical vulnerabilities, the SBOM analysis also uncovered several instances where the bundled SDKs and native libraries were not properly sandboxed or isolated from the rest of the application. This meant that a vulnerability in one component could potentially affect other parts of the app, leading to cascading failures or security breaches. For example, a native library responsible for handling file I/O operations was found to have a race condition that could allow attackers to overwrite files in the app’s private directory. This vulnerability was not isolated to the library itself but could also affect other components that accessed the same directory, such as the app’s data storage and user authentication modules.

The SBOM analysis further revealed that some of the native libraries and SDKs were not properly configured for secure memory management, leading to potential information leaks. For example, one of the SDKs used a shared memory buffer without proper initialization, allowing attackers to access sensitive data such as session tokens and user credentials. This was particularly concerning given the app’s use of encrypted databases and the fact that it stored user data locally on the device. The lack of secure memory management in these components increased the risk of data exposure, especially if the app was running on a compromised device.

Overall, the SBOM analysis of LegacyApp highlighted several critical issues related to the use of outdated native libraries and bundled SDKs. These included versioning inconsistencies, unnecessary dependencies, licensing and privacy concerns, and the absence of modern security protections such as stack guards and memory sanitization. The findings underscored the importance of maintaining up-to-date components, implementing proper dependency management, and ensuring that all bundled libraries and SDKs adhere to modern security standards. By addressing these issues, developers can significantly reduce the attack surface of their applications and improve the overall security posture of their mobile apps.

### Case Study: Privacy-Centric Mobile App with Minimal SDKs and Custom Components

This architectural choice was deliberate, aimed at reducing the attack surface and ensuring compliance with stringent privacy regulations such as GDPR and CCPA.

The app's development process began with a thorough assessment of required functionalities. The core features included secure login via biometric authentication, end-to-end encryption for transaction data, and a lightweight payment gateway. To implement these features, the development team selected components that were known for their security credentials and minimal data collection practices. For example, the biometric authentication was handled by an in-house cryptographic library, **CryptoKit v2.1**, which was developed using the **OpenSSL** framework. This library was chosen over commercial SDKs to ensure greater control over data handling and reduce reliance on external vendors.

The payment gateway integration involved a proprietary API that communicated directly with the financial institution's backend, bypassing the need for third-party SDKs. This approach not only reduced the number of components in the app but also minimized the potential for data leaks or unauthorized access. The app’s user interface was built using **React Native**, a framework known for its performance and cross-platform compatibility, which allowed the development team to maintain a consistent experience across both iOS and Android platforms without introducing unnecessary dependencies.

To further enhance privacy, the app’s data collection practices were limited to essential user identifiers such as email addresses and device information, with explicit opt-in consent mechanisms for any additional data tracking. The development team also implemented a **data minimization policy**, ensuring that only the necessary data was collected and stored. The app’s architecture was designed to be modular, allowing for easy updates and maintenance without introducing new vulnerabilities. The development team used a **dependency management system** that allowed them to track all components, including native libraries and bundled SDKs, and ensure that each component met the required security standards. This system also facilitated the integration of **CycloneDX SBOM**, which provided a detailed inventory of all components used in the app. The SBOM included information on the version numbers, licenses, and dependencies of each component, enabling the team to identify and mitigate potential security risks.

One of the key challenges in developing SecurePay was ensuring that the minimal SDK approach did not compromise functionality. To address this, the development team conducted extensive testing and validation processes. They used **static analysis tools** such as **SonarQube** and **Coverity** to identify potential vulnerabilities in the codebase and ensure that all components adhered to security best practices. Additionally, they performed **dynamic analysis** using **OWASP ZAP** to simulate real-world attack scenarios and test the app’s resilience against common threats.

The team also integrated **CI/CD pipelines** that automated the SBOM generation and vulnerability scanning processes. This allowed them to continuously monitor the app’s components for updates and security patches, ensuring that any new vulnerabilities were addressed promptly. The use of **CycloneDX SBOM** was instrumental in this process, as it provided a clear and structured inventory of all components, making it easier to track dependencies and identify potential risks.

In terms of privacy compliance, the development team worked closely with legal and compliance officers to ensure that the app met all regulatory requirements. They conducted **privacy impact assessments (PIAs)** to evaluate the data collection practices and identify any potential privacy risks. These assessments were informed by the use of **CycloneDX SBOM**, which provided detailed information on the components used in the app and their data handling practices. This information was crucial in ensuring that the app’s design aligned with the principles of transparency, consent, and data minimization.

The development team also implemented **user consent mechanisms** that allowed users to control their data collection preferences. For example, users could opt out of certain data tracking features, such as analytics or location services, without affecting the core functionality of the app. This approach not only enhanced user trust but also aligned with the principles of **privacy by design**, a key tenet of GDPR and other privacy regulations.

In addition to the technical aspects, the team conducted **user education campaigns** to inform users about the app’s data practices. These campaigns included in-app notifications, help guides, and FAQs that explained how the app collected and used user data. The use of **CycloneDX SBOM** played a role in these efforts by providing a transparent view of the app’s components and their data handling practices, allowing users to make informed decisions about their privacy.

The development of SecurePay also involved collaboration with third-party auditors to ensure that the app met industry standards for security and privacy. These auditors used **CycloneDX SBOM** as part of their evaluation process, analyzing the app’s components for potential vulnerabilities and ensuring that all components were up-to-date and compliant with relevant security standards. This collaborative approach helped to identify any gaps in the app’s security posture and provided actionable recommendations for improvement.

Overall, the development of SecurePay exemplified a privacy-centric approach to mobile app design. By minimizing the use of third-party SDKs and focusing on essential components, the team was able to reduce the attack surface and enhance user trust. The integration of **CycloneDX SBOM** played a critical role in this process, providing a structured inventory of all components and enabling continuous monitoring for security and privacy risks. Through rigorous testing, compliance assessments, and user education, the team ensured that SecurePay met the highest standards of security and privacy, setting a benchmark for future mobile app development.

By unpacking native libraries and bundled SDKs, developers can gain a detailed understanding of their application's component dependencies and potential vulnerabilities. The matching of components against known-vulnerability and privacy databases provides a proactive approach to identifying and mitigating security risks. This case study serves as a practical example of how CycloneDX can be used to generate accurate and actionable SBOMs for complex mobile applications, ensuring that security and compliance are addressed at the earliest stages of development.
